# 화면 설계

Thymeleaf 기반 관리·검증 화면. 기능은 전부 기존 REST API 위에 얹는다.

## 설계 원칙

### 1. Thymeleaf 는 페이지 껍데기, 동작은 기존 REST

서버는 뷰만 렌더링하고 실제 동작은 브라우저에서 `fetch` 로 기존 엔드포인트를 호출한다.

```
GET /ui        ->  Thymeleaf 렌더 (빈 화면)
브라우저 fetch  ->  POST /documents, GET /rag-chat-streams, /plain-chat-streams, /chat-streams
```

**대안(서버사이드 폼 POST + `Model`)을 쓰지 않은 이유**

| 항목 | fetch 방식 | 폼 POST 방식 |
|---|---|---|
| 서비스 호출 경로 | REST 컨트롤러 하나 | REST + UI 컨트롤러로 이원화 |
| 기존 REST 컨트롤러 | 무변경 | 무변경이나 로직 중복 발생 |
| 스트리밍(`/chat-streams`) | 가능 | 불가 |
| RAG vs 일반 동시 호출 | 병렬 호출 후 각각 표시 | 순차 처리, 화면 새로고침 |

이 프로젝트의 핵심 가치는 **RAG 유무 비교**다. 두 엔드포인트를 병렬로 호출해 나란히
보여주려면 클라이언트 측 호출이 필요하다. 또한 REST API 를 유일한 진입점으로 두면
Swagger 로 검증한 동작과 화면 동작이 어긋나지 않는다.

### 2. 신규 백엔드는 목록·삭제 두 개만

화면 때문에 추가한 백엔드는 다음 두 엔드포인트뿐이다. 나머지는 기존 API 를 그대로 쓴다.

| Method | Path | 추가 이유 |
|---|---|---|
| `GET` | `/documents` | 적재된 문서를 나열하려면 조회 수단이 필요. `VectorStore` 에는 목록 API 가 없음 |
| `DELETE` | `/documents?source=` | 화면에서 문서 단위 삭제 |
| `POST` | `/documents/analysis` | 적재 전 청킹 결과 확인. 저장·임베딩 없는 미리보기 |

목록 조회는 `VectorStore` 로 불가능해 `JdbcTemplate` 으로 `vector_store` 테이블을 직접 읽는다.
테이블명은 `spring.ai.vectorstore.pgvector.table-name` 을 주입해 설정과 어긋나지 않게 한다.

### 3. JS 는 `static/` 에 분리

Thymeleaf 3 은 `<script>` 블록에 JavaScript 인라이닝을 적용한다. 템플릿 안에 스크립트를
두면 특정 문자열이 템플릿 표현식으로 해석될 수 있다. 정적 파일로 분리하면
Thymeleaf 가 전혀 건드리지 않으며 관심사도 분리된다.

## 라우팅

`UiController` 는 뷰 이름만 반환한다. 로직 없음.

| Path | 템플릿 | 화면 |
|---|---|---|
| `/` | — | `/ui` 로 리다이렉트 |
| `/ui` | `chat.html` | RAG 비교 채팅 (메인) |
| `/ui/documents` | `documents.html` | 문서 적재 + 목록/삭제 |
| `/ui/stream` | `stream.html` | 스트리밍 채팅 |

**업로드 화면과 목록 화면을 한 페이지에 합친 이유** — 적재 직후 결과를 바로 목록에서
확인하는 흐름이 자연스럽다. 페이지를 나누면 업로드 후 이동해야 목록을 볼 수 있다.
두 기능은 모두 제공되며 위치만 같다.

## 템플릿 구조

```
templates/
├── fragments/layout.html   # head(pageTitle), nav(active), scripts 프래그먼트
├── chat.html               # RAG 비교
├── documents.html          # 적재 + 목록
└── stream.html             # 스트리밍

static/
├── css/app.css             # Bootstrap 위 최소 보정
└── js/
    ├── markdown.js         # 세 화면 공용 마크다운 렌더 (layout 프래그먼트가 로드)
    ├── chat.js
    ├── documents.js
    └── stream.js
```

레이아웃은 `th:fragment` + `th:replace` 로만 구성한다. `thymeleaf-layout-dialect`
같은 추가 의존성은 쓰지 않는다 — 프래그먼트 3개로 충분하다.

```html
<head th:replace="~{fragments/layout :: head('RAG 비교 채팅')}"></head>
<nav  th:replace="~{fragments/layout :: nav('chat')}"></nav>
<footer th:replace="~{fragments/layout :: scripts}"></footer>
```

`nav(active)` 에 현재 화면 키를 넘기면 해당 링크에 `active` 클래스와
`aria-current="page"` 가 붙는다.

## 화면별 설계

### /ui — RAG 비교 채팅

```
┌────────────────────────────────────────────────────────────┐
│ vibe-llm   [RAG 비교 채팅] 문서  스트리밍        Swagger   │
├────────────────────────────────────────────────────────────┤
│ RAG 비교 채팅                        [문서 적재하기 →]     │
│ 같은 질문을 두 스트리밍 엔드포인트에 동시에 보냅니다       │
│                                                            │
│ ┌────────────────────────────────────────────────────────┐ │
│ │ 질문                                                   │ │
│ │ [                                                    ] │ │
│ │ conversationId [ui-default]   [전송] [초기화]          │ │
│ └────────────────────────────────────────────────────────┘ │
│                                                            │
│ ┌─── RAG · 근거 기반 ───┐  ┌─── 일반 · RAG 없음 ───┐      │
│ │ /rag-chat-streams     │  │ /plain-chat-streams   │      │
│ │                       │  │                       │      │
│ │ SEV-2 는 단일 기능    │  │ ⠋ 생성 중…            │      │
│ │ 중단을 뜻합니다.      │  │                       │      │
│ │ 근거: spec.do▊        │  │  ← 각 패널이 독립적으로│      │
│ │  ← 토큰 도착하는 대로 │  │     스트리밍된다       │      │
│ └───────────────────────┘  └───────────────────────┘      │
└────────────────────────────────────────────────────────────┘
```

- 두 호출을 **병렬로** 보내고 `Promise.allSettled` 로 기다린다. 두 패널이 각각
  도착하는 대로 **동시에 스트리밍**된다.
- 각 패널은 `대기 → 스피너 → 스트리밍 → 완료` 4상태. 첫 토큰이 도착하면 스피너를
  내리고 답변 영역을 연다. 한쪽이 실패해도 다른 쪽은 그대로 진행된다.
- **응답은 마크다운으로 렌더한다.** 모델이 제목·표·코드블록을 마크다운으로 내보내므로
  평문으로 두면 `##`, `|---|`, ``` 기호가 그대로 보인다. 렌더는 공용
  `streamMarkdown()` 이 맡는다 — 누적 전체 재렌더 + 100ms 제한.
- 실패한 패널만 `text-danger` 로 표시하고 상태 코드와 응답 앞부분을 함께 보여준다.
  **실패 메시지는 렌더하지 않는다** — 우리가 만든 문자열이라 마크다운이 아니다.
  실패 판정은 본문을 읽기 전에 상태 코드로 한다. 스트리밍이 시작된 뒤 끊기면 그 시점까지
  렌더된 내용은 화면에 남는다.

#### 왜 스트리밍 엔드포인트를 새로 만들었나

비교 화면은 `/rag-chat-streams` 와 `/plain-chat-streams` 를 쓴다. 기존 엔드포인트를
재사용하지 않은 이유:

| 후보 | 기각 이유 |
|---|---|
| `/rag-chats`, `/chats` | 동기 응답이라 스트리밍 불가 |
| `/chat-streams` (일반 패널용) | `user-message.st` 를 적용해 질문이 "«X» 개념을 상세히 설명해 주세요." 로 바뀐다. RAG 패널은 원본 질문을 쓰므로 **두 패널의 user 메시지가 달라져 비교가 무의미해진다** |
| 기존 엔드포인트에 `stream=true` 플래그 | ADR-0003 에서 같은 이유로 기각한 패턴 |

새 엔드포인트 둘은 각각 `/rag-chats`·`/chats` 와 프롬프트·어드바이저·메모리 키 전달
방식이 **완전히 같다.** `.call()` 이 `.stream()` 으로 바뀐 것뿐이다. 기존 세 엔드포인트는
무변경이라 curl 검증 절차도 그대로다.

RAG 패널의 첫 조각이 더 늦게 도착한다 — 검색과 증강이 첫 토큰 전에 끝나야 하기 때문이다.
이 지연 차이 자체가 RAG 비용을 눈으로 보여준다.
- `conversationId` 는 `/rag-chat-streams` 의 쿼리 파라미터와 `/plain-chat-streams` 의
  `userId` 헤더에 함께 쓴다.
  두 엔드포인트의 메모리 키 전달 방식이 다르기 때문이다.
- RAG 패널을 `border-primary-subtle` 로 강조해 어느 쪽이 근거 기반인지 시각적으로 구분한다.

### /ui/documents — 분석 → 적재 + 목록

적재는 **2단계**다. 분석하기로 청킹 결과를 확인해야 적재하기가 활성화된다.

```

│ 문서                                                           │

│                                                                │
│ ┌─ 적재 ──────────────────────────────────────────────────┐   │
│ │ 파일 [파일 선택] spec.docx   [ 분석하기 ] [ 적재하기 ]   │   │
│ │ docling-serve 가 처리하는 모든 형식 · 최대 20MB           │   │
│ │ 먼저 분석하기 로 청킹 결과를 확인한 뒤 적재하기 가 활성화 │   │

#### 2단계 흐름

| 상태 | 분석하기 | 적재하기 | 분석 결과 |
|---|---|---|---|
| 초기 | 활성 | **비활성** | 숨김 |
| 분석 완료 | 활성 | **활성** | 표시 |
| 파일 변경 | 활성 | **비활성** | 숨김 (초기화) |
| 적재 완료 | 활성 | **비활성** | 숨김 (초기화) |

**분석 단계는 부수효과가 없다.** `POST /documents/analysis` 는 파싱과 청킹까지만
수행하고 벡터 스토어에 쓰지 않으며 임베딩도 호출하지 않는다. 임베딩은 적재 단계에서
한 번만 일어나므로, 확인 절차를 넣었다고 임베딩 비용이 두 배가 되지 않는다.

청크 경계는 `analyze()` 와 `ingest()` 가 같은 docling 엔드포인트를 같은 파라미터로
호출하므로 **분석 결과가 실제 적재 결과와 일치한다.**

**파싱 결과를 마크다운으로 렌더해서 보여준다.** docling 의 출력은 제목·표·목록 구조를
살린 마크다운이다. 평문으로 보여주면 파서를 바꾼 효과가 화면에서 보이지 않으므로,
`marked` 로 파싱하고 `DOMPurify` 로 정화한 뒤 렌더한다. 문서에서 온 문자열을 `innerHTML`
에 넣는 것이므로 정화는 선택이 아니다. 원문 마크다운도 토글로 볼 수 있게 둔다.

청크 미리보기도 같은 경로로 렌더하되 **자르지 않는다.** 이전에는 160자로 잘라 보여줬는데,
마크다운을 중간에서 자르면 표나 강조가 깨진 채로 렌더된다. docling 청크는 토큰 상한이
있어 전문을 그대로 보여줘도 길이가 감당된다.

**파일을 바꾸면 분석 결과를 버리고 적재하기를 다시 잠근다.** 분석한 파일과 적재할 파일이
어긋나는 것을 막기 위해, 분석 시점의 `File` 객체를 들고 있다가 적재 때 그 객체를 보낸다.
적재는 서버에서 다시 파싱한다 — 분석 결과를 서버에 캐시하지 않으므로 상태 관리가 필요 없다.
docling 파싱은 CPU 이미지에서 결코 싸지 않지만, 캐시를 도입하면 서버 상태와 만료 관리가
따라붙는다. 학습 프로젝트 규모에서는 단순함을 택했다.

**이미 적재된 문서면 교체 경고를 띄운다.** 기존 청크 수와 적재 시각을 함께 보여주므로
덮어쓰기를 인지한 상태에서 적재할 수 있다.

**토큰 수는 근사치다.** docling HybridChunker 의 토크나이저(`all-MiniLM-L6-v2`) 기준이며
임베딩 모델(Qwen3)의 실제 토크나이저와 다르다. 표 캡션에 이 점을 밝힌다.

- 페이지 진입 시와 적재·삭제 후에 목록을 다시 불러온다.
- `chunks: 0` 은 **경고(warning)** 로 구분해 표시한다. 오류가 아니라 docling 이 추출한
  텍스트가 없다는 뜻이므로, 성공과 같은 색으로 보여주면 오해를 낳는다.
- 분석 중에는 docling CPU 변환이 수십 초 걸릴 수 있음을 안내한다. 분석은 청킹과 마크다운
  변환으로 docling 을 두 번 호출하므로 적재보다 느리다.
- 적재 중에는 버튼을 비활성화하고 임베딩 호출로 시간이 걸릴 수 있음을 안내한다.
  로컬 임베딩 모델은 첫 호출에 모델 로딩 시간이 포함될 수 있다.
- 시각은 브라우저 현지 시간으로 표시한다. 저장값은 UTC ISO-8601 문자열이다.

#### 삭제 확인은 Bootstrap 모달

삭제는 되돌릴 수 없으므로 확인 단계를 둔다. 네이티브 `confirm()` 대신 Bootstrap 모달을 쓴다.

- 브라우저 모달 대화상자는 페이지의 모든 이벤트를 막아 자동화 도구가 응답할 수 없게 만든다.
- 모달 본문에 되돌릴 수 없다는 점과 재업로드가 필요하다는 점을 명시한다.

### /ui/stream — 스트리밍 채팅

```
┌────────────────────────────────────────────────────────────┐
│ 스트리밍 채팅                                              │
│ 개념 [record]  conversationId [ui-stream]      [전송]      │
│                                                            │
│ ┌─ 응답 ──────────────────────────────── [수신 중] ────┐  │
│ │ Java Records          ← h1 으로 렌더                  │  │
│ │ Problem Analysis      ← h2 로 렌더                    │  │
│ │ ┌───────────────────┐ ← 코드블록으로 렌더             │  │
│ │ │ record Point(...) │                                 │  │
│ │ └───────────────────┘                                 │  │
│ └───────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────┘
```

- 스트림 읽기와 렌더는 공용 `streamMarkdown()` 이 맡는다. 비교 화면과 로직이 같아
  `static/js/markdown.js` 로 뺐다.
- `/chat-streams` 는 JSON 배열이 아니라 평문 청크로 응답한다.
- `TextDecoder` 에 `stream: true` 를 주어 멀티바이트 한글이 청크 경계에서 깨지지 않게 한다.
  마지막에 `decode()` 를 한 번 더 호출해 남은 바이트를 비운다.
- **누적 전체를 다시 렌더한다.** 마크다운은 부분 문자열만으로 파싱할 수 없다 — 열린
  코드 펜스나 표 헤더가 청크 경계에 걸리면 조각만 봐서는 의미가 정해지지 않는다.
- **재렌더는 100ms 로 제한한다.** 토큰마다 전체를 파싱하면 응답이 길어질수록 느려진다.
  스트림이 끝나면 제한 없이 한 번 더 렌더해 마지막 조각이 누락되지 않게 한다.
- 출력 요소는 `<pre>` 가 아니라 `<div>` 다. 렌더 결과가 블록 요소를 포함하므로
  `<pre>` 안에 넣을 수 없다. 코드 폰트는 렌더된 `pre`/`code` 가 받는다.
- 상태 배지로 `대기 → 연결 중 → 수신 중 → 완료/실패` 를 표시한다.
- 출력이 늘어날 때마다 스크롤을 하단으로 따라가게 한다.

## 스타일

**Bootstrap 5.3 CDN** + `static/css/app.css` 최소 보정.

```html
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/css/bootstrap.min.css">
<script src="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/js/bootstrap.bundle.min.js"></script>
```

마크다운 렌더 라이브러리는 `fragments/layout.html :: scripts` 에서 전역으로 싣는다.

```html
<script src="https://cdn.jsdelivr.net/npm/marked@15.0.7/marked.min.js"></script>
<script src="https://cdn.jsdelivr.net/npm/dompurify@3.2.4/dist/purify.min.js"></script>
<script th:src="@{/js/markdown.js}"></script>
```

세 화면이 모두 쓰기 때문이다 — 채팅은 두 응답 패널, 스트리밍은 출력, 문서는 파싱 결과와
청크. `markdown.js` 는 둘을 노출한다.

| 함수 | 용도 | 쓰는 곳 |
|---|---|---|
| `renderMarkdown(target, source)` | 완성된 문자열 1회 렌더 | 문서 화면 |
| `streamMarkdown(target, response, onFirstChunk)` | 응답 스트림을 읽어 점진 렌더 | 비교 채팅, 스트리밍 |

`onFirstChunk` 는 첫 조각 도착 시 한 번 호출된다. 비교 채팅이 스피너를 내리는 데 쓴다.

CDN 의존이므로 **오프라인 환경에서는 스타일이 깨진다.** LLM·DB·docling 이 모두 로컬이라
네트워크 없이도 기능은 동작하지만 레이아웃은 무너지고, `marked`/`DOMPurify` 가 없으면
렌더 시점에 `ReferenceError` 가 난다. 오프라인 사용이 필요하면 세 라이브러리를
`static/` 에 내려 두고 경로를 바꾼다.

`app.css` 가 담당하는 것:

| 규칙 | 이유 |
|---|---|
| `.markdown-body pre` 배경 | 렌더된 코드 블록이 본문과 구분되지 않는다 |
| `word-break: break-word` | 긴 식별자·URL 이 레이아웃을 밀어내지 않게 |
| `max-height` + `overflow-y` | 긴 답변이 페이지를 무한정 늘이지 않게 |
| `min-height` (lg 이상) | 두 비교 패널 높이가 달라도 정렬 유지 |
| 한글 폰트 스택 | `Malgun Gothic`, `D2Coding` 포함 |
| `.markdown-body table` 테두리 | 렌더된 표는 Bootstrap 의 `.table` 클래스를 못 받는다 |
| `.markdown-cell > :last-child` 여백 제거 | 청크 셀 안 마크다운이 표 행을 늘이지 않게 |

## 접근성 · 반응형

- 모든 입력에 `<label for>` 연결. placeholder 를 라벨 대용으로 쓰지 않는다.
- 비동기로 갱신되는 영역에 `aria-live="polite"` — 답변 패널, 적재 결과, 스트림 출력.
- 스피너 아이콘은 `aria-hidden="true"`, 상태는 텍스트로 전달한다.
- 현재 메뉴에 `aria-current="page"`.
- 표에 `<caption>` 과 `scope="col"` 지정.
- 모달에 `aria-labelledby`, 닫기 버튼에 `aria-label`.
- Bootstrap 그리드(`col-lg-6`, `col-md-*`)로 좁은 화면에서는 비교 패널이 세로로 쌓인다.
- 네비게이션은 `navbar-toggler` 로 모바일에서 접힌다.

## 화면에서 드러나는 제약

| 제약 | 화면 처리 |
|---|---|
| 한글 쿼리 인코딩 | `encodeURIComponent` 로 항상 인코딩. 터미널 `curl` 과 달리 화면에서는 문제없음 |
| 20MB 업로드 한도 | 입력 아래 안내 문구, 초과 시 413 메시지 노출 |
| 임베딩 콜드 스타트 | 적재 중 안내 문구 + 버튼 비활성화 |
| LM Studio 미기동 | 패널별 오류 메시지에 상태 코드와 응답 앞부분 표시 |
| `chunks: 0` | 성공이 아닌 경고로 구분 |
